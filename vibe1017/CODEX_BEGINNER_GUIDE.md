# Codex 초보자를 위한 기초 설정 및 사용 안내

Codex는 자연어로 요청을 받아 코드 작성, 파일 수정, 테스트 실행, Git 작업을 돕는 개발 보조 도구입니다. 이 문서는 처음 사용하는 사람이 안전하게 프로젝트를 열고, 원하는 작업을 명확히 요청하고, 결과를 확인하는 방법을 안내합니다.

## 1. 시작하기 전에 준비할 것

Codex를 편하게 사용하려면 다음 항목이 있으면 좋습니다.

- 작업할 GitHub 저장소 또는 로컬 프로젝트
- 프로젝트의 목적과 현재 해결하려는 문제에 대한 간단한 설명
- 사용하는 언어와 실행 방법에 대한 정보(알고 있다면)
- GitHub 연결 또는 저장소에 변경을 올릴 권한

프로젝트를 잘 모르는 경우에도 괜찮습니다. `이 저장소의 구조와 실행 방법을 먼저 알려줘`라고 요청하면 Codex가 파일과 설정을 살펴본 뒤 설명할 수 있습니다.

## 2. Codex가 작업하는 위치 이해하기

클라우드 환경에서 Codex는 일반적으로 제공된 작업 공간 안의 저장소를 수정합니다. 예를 들어 `/workspace/my-project` 같은 경로에 파일이 있을 수 있습니다.

이 파일은 곧바로 개인 컴퓨터에 저장되지 않습니다. 컴퓨터에서 받으려면 다음 중 하나를 사용합니다.

1. GitHub에 커밋과 푸시를 요청한 뒤 컴퓨터에서 `git pull`을 실행합니다.
2. 서비스 화면에서 지원하는 다운로드 또는 파일 내보내기 기능을 사용합니다.

GitHub에 반영하고 싶다면 요청에 `커밋하고 main 브랜치에 푸시해줘`처럼 명시합니다.

## 3. 처음 환경을 설정하는 방법

새 저장소를 열었다면 가장 먼저 개발 환경을 확인합니다. 다음처럼 요청할 수 있습니다.

```text
이 저장소의 개발 환경을 설정해줘. README와 설정 파일을 확인하고,
필요한 의존성을 설치한 뒤 실행 또는 테스트까지 검증해줘.
```

Codex는 보통 다음을 확인합니다.

- `README.md`와 프로젝트별 안내 파일
- `package.json`, `pyproject.toml`, `requirements.txt` 같은 의존성 설정
- Node.js, Python 등 필요한 실행 도구의 버전
- 개발 서버, 빌드, 테스트 명령
- 필요한 환경 변수와 외부 서비스 연결

비밀번호나 API 키가 필요한 경우에는 값을 채팅에 적지 마세요. 환경 설정의 비밀값 입력 기능을 사용하고, Codex에는 `API 키가 환경 변수로 설정되어 있어`처럼 알려 주면 됩니다.

## 4. 좋은 요청을 쓰는 법

요청에는 목표, 범위, 완료 기준을 넣으면 결과가 더 정확해집니다.

### 간단한 요청

```text
로그인 버튼의 색상을 파란색으로 바꿔줘.
```

### 더 좋은 요청

```text
로그인 화면의 기본 버튼 색상을 #2563eb로 바꿔줘.
호버와 키보드 포커스 상태도 읽기 쉽게 조정하고,
관련 화면이 깨지지 않는지 확인해줘.
```

### 요청에 포함하면 좋은 정보

| 항목 | 예시 |
| --- | --- |
| 목표 | “회원가입 폼을 추가해줘” |
| 대상 | “`src/pages/Signup.tsx`를 중심으로” |
| 조건 | “모바일에서도 사용할 수 있게” |
| 완료 기준 | “유효성 검사와 테스트가 통과해야 함” |
| 제한 | “기존 API 형식은 변경하지 마” |

파일 위치를 모르거나 구현 방향이 확실하지 않다면 먼저 선택지를 요청해도 좋습니다.

```text
이 기능을 추가하려면 어떤 파일을 수정해야 하는지 조사하고,
권장 구현 방법을 설명해줘. 아직 코드는 수정하지 마.
```

## 5. 자주 쓰는 요청 예시

### 코드 이해와 조사

```text
이 프로젝트의 폴더 구조와 실행 흐름을 초보자도 이해할 수 있게 설명해줘.
```

```text
결제 금액이 계산되는 코드를 찾아서 데이터 흐름을 설명해줘.
```

### 기능 개발

```text
할 일 목록에 완료 처리 기능을 추가해줘.
완료된 항목은 취소선으로 표시하고, 새로고침 후에도 상태가 유지되게 해줘.
```

### 버그 수정

```text
모바일에서 메뉴가 화면 밖으로 밀려나는 문제를 재현하고 원인을 찾아 고쳐줘.
수정 후 관련 테스트나 화면 검증을 실행해줘.
```

### 문서 작성

```text
이 프로젝트의 설치, 실행, 테스트 방법을 README에 정리해줘.
실제로 확인한 명령만 기록해줘.
```

### GitHub 반영

```text
변경 사항을 검토하고 관련 파일만 커밋한 뒤 main 브랜치에 푸시해줘.
커밋 메시지는 영어로 간결하게 작성해줘.
```

## 6. 작업 결과를 확인하는 방법

Codex가 작업을 마치면 다음을 확인합니다.

- 어떤 파일을 바꿨는지
- 어떤 명령이나 테스트를 실행했는지
- 테스트 성공과 실패 여부
- 남아 있는 제한 사항 또는 필요한 사용자 작업
- GitHub 반영 여부와 커밋 식별자

결과가 기대와 다르면 구체적으로 피드백합니다.

```text
버튼의 위치는 좋지만 문구를 “저장하기”로 바꿔줘.
모바일 화면에서는 너비를 화면 전체로 사용하게 해줘.
```

원하는 부분만 바꾸도록 `다른 파일은 수정하지 말아줘` 또는 `먼저 변경 계획만 보여줘`라고 지정할 수도 있습니다.

## 7. 파일과 Git의 기본 흐름

GitHub에 변경을 올리는 일반적인 과정은 아래와 같습니다.

```mermaid
flowchart LR
    A[파일 수정] --> B[변경 내용 확인]
    B --> C[테스트 또는 실행]
    C --> D[Git 커밋]
    D --> E[GitHub 푸시]
    E --> F[내 컴퓨터에서 git pull]
```

Codex에게 GitHub 반영을 요청하면 보통 변경 범위를 확인하고 커밋한 뒤 원격 저장소로 푸시합니다. 푸시는 공유 브랜치를 바꾸는 작업이므로, 어떤 브랜치에 올릴지 명확히 말하는 것이 좋습니다.

개인 컴퓨터에서 최신 변경을 받으려면 저장소 폴더에서 다음을 실행합니다.

```bash
git pull origin main
```

컴퓨터에 아직 저장소가 없다면 한 번만 복제합니다.

```bash
git clone https://github.com/계정이름/저장소이름.git
cd 저장소이름
```

## 8. 권한 요청 이해하기

Codex가 의존성을 설치하거나 원격 저장소에 푸시하려면 권한 승인을 요청할 수 있습니다. 승인 창에서는 다음을 확인합니다.

- 실행하려는 명령이 무엇인지
- 어떤 파일 또는 네트워크에 접근하는지
- 요청한 작업과 관련 있는지

내용이 요청과 맞지 않거나 이해하기 어렵다면 승인하지 말고 이유를 물어보세요. 삭제, 초기화, 대량 변경처럼 되돌리기 어려운 작업은 대상과 영향을 먼저 확인하는 것이 좋습니다.

## 9. 안전하게 사용하는 습관

- API 키, 비밀번호, 인증 토큰을 채팅이나 코드에 직접 넣지 않습니다.
- `.env` 파일은 보통 Git에 올리지 않도록 설정합니다.
- 대규모 수정 전에는 현재 변경 사항을 확인합니다.
- 공유 브랜치에 푸시하기 전에는 대상 브랜치를 명확히 합니다.
- 테스트 결과를 확인하고, 실패가 있으면 원인과 영향 범위를 묻습니다.
- 이해하지 못한 명령은 실행 목적을 설명해 달라고 요청합니다.

예를 들어 다음 요청은 안전한 작업 범위를 분명히 합니다.

```text
삭제 명령이나 데이터베이스 변경은 실행하지 말고,
먼저 영향 범위와 수정 제안만 알려줘.
```

## 10. 문제가 생겼을 때 요청하는 방법

오류가 발생했다면 오류 메시지, 재현 순서, 기대한 결과를 함께 알려 주세요.

```text
`npm run dev` 실행 후 로그인 버튼을 누르면 오류가 발생해.
브라우저 콘솔에는 “...” 메시지가 보이고,
정상이라면 대시보드로 이동해야 해. 원인을 조사하고 수정해줘.
```

추측만으로 고치기보다, 재현 가능한 증상과 로그를 바탕으로 원인을 확인하게 요청하는 편이 좋습니다. 민감한 값은 오류 로그를 공유하기 전에 가립니다.

## 11. 추천 작업 순서

처음 프로젝트를 다룰 때는 아래 순서가 안정적입니다.

1. 저장소 구조와 실행 방법을 파악합니다.
2. 의존성을 설치하고 기존 테스트 또는 실행을 확인합니다.
3. 작은 기능 하나를 명확한 완료 기준과 함께 요청합니다.
4. 변경 파일과 검증 결과를 검토합니다.
5. 만족하면 커밋과 푸시를 요청합니다.
6. 컴퓨터에서 `git pull`로 변경을 받습니다.

처음부터 큰 기능을 한 번에 요청하기보다 작은 단위로 나누면 결과를 검토하고 방향을 조정하기 쉽습니다.

## 12. 바로 시작할 수 있는 첫 요청

다음 문장을 복사해 현재 프로젝트에 맞게 사용해 보세요.

```text
이 저장소를 처음 보는 개발자라고 생각하고,
프로젝트 구조와 실행 방법을 조사해줘.
수정은 하지 말고, 필요한 도구와 가장 먼저 실행할 명령을 알려줘.
```

그 다음에는 다음처럼 이어갈 수 있습니다.

```text
설명한 개발 환경을 설정하고 기존 테스트를 실행해줘.
문제가 있으면 원인과 해결 방법을 알려줘.
```

이 문서는 Codex 사용의 기본 흐름을 설명합니다. 프로젝트마다 사용 기술과 배포 방식이 다르므로, 실제 명령은 해당 저장소의 README와 설정 파일을 함께 확인하세요.
